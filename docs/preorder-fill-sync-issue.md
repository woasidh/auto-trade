# 선주문/체결동기화형 전환 이슈

작성일: 2026-06-27

## 배경

현재 자동매매 러너는 매 틱마다 현재가를 조회한 뒤, 전략 조건을 평가해서 매수 또는 매도 주문을 접수한다. PAPER 모드에서는 주문이 접수되면 곧바로 체결하지 않고 `ACCEPTED` 상태로 두었다가, 설정된 지연 시간이 지난 뒤 다시 현재가를 보고 체결 또는 취소를 판단한다.

이 구조에서는 가격이 이미 슬롯 매수가 또는 목표 매도가를 터치해서 전략 조건을 만족했더라도, 다음 동기화 시점의 현재가가 지정가 반대편으로 이동하면 PAPER 주문이 취소될 수 있다. 사용자 관점에서는 "조건을 만족했는데 체결되지 않은" 것처럼 보인다.

## 현재 흐름

```text
현재가 조회
-> 이전 관측가와 현재 관측가로 조건 평가
-> 조건 만족 시 주문 접수
-> 슬롯 BUY_PENDING 또는 SELL_PENDING
-> 일정 시간 후 주문 동기화
-> 동기화 시점 현재가로 체결 가능 여부 재판단
-> 체결 또는 취소
```

현재 매수 조건은 다음과 같다.

- 슬롯 상태가 `EMPTY`
- 이전 관측가와 현재 관측가 사이의 가격 구간이 슬롯 매수가를 터치 또는 통과
- 최근 매수 주문이 취소, 거절, 실패된 슬롯이면 현재가가 매수가 이하일 때 재시도 가능
- 단, 한 틱의 매수 평가 가격 변화폭이 `defaultMaxBuyPriceGap`를 초과하면 매수 평가를 건너뜀

현재 매도 조건은 다음과 같다.

- 슬롯 상태가 `HOLDING`
- 현재가가 슬롯 목표 매도가 이상

## 제안 방향

조건감시형에서 선주문/체결동기화형으로 전환한다.

핵심은 러너가 "가격 조건이 만족됐는지"를 보고 그때 주문을 넣는 방식이 아니라, 슬롯별로 있어야 할 지정가 주문을 미리 유지하고, 이후 거래소 또는 PAPER 주문 상태를 동기화해서 슬롯 상태를 갱신하는 방식이다.

```text
전략 시작 또는 복구
-> 현재가 조회
-> 주문 상태 동기화
-> 슬롯별 필요 주문 계산
-> EMPTY 슬롯에는 매수 지정가 주문 유지
-> 매수 체결 확인 시 HOLDING 처리
-> HOLDING 슬롯에는 목표 매도 지정가 주문 유지
-> 매도 체결 확인 시 EMPTY 처리
-> 다시 매수 지정가 주문 유지
```

## 매수 흐름

전략 시작 또는 복구 시 현재가보다 아래에 있는 `EMPTY` 슬롯에 매수 지정가 주문을 미리 접수한다.

예를 들어 현재가가 `1519`이고 슬롯 매수가가 `1500, 1498, 1496 ... 1450`이면, 모든 매수가는 현재가 아래에 있으므로 각 슬롯에 매수 지정가 주문을 걸 수 있다.

```text
EMPTY
-> 매수 지정가 주문 접수
-> BUY_PENDING
-> 주문 동기화에서 매수 체결 확인
-> fill 저장
-> HOLDING
```

주의할 점은 전략 시작 또는 재시작 시 현재가보다 위에 있는 매수 지정가를 바로 접수하면 즉시 체결될 수 있다는 점이다. 이는 미관측 구간을 소급 매수하는 효과가 될 수 있으므로 보수적으로 제한한다.

권장 가드:

- 현재가보다 아래에 있는 매수 슬롯만 선주문
- 현재가와 같은 매수 슬롯은 정책으로 허용 가능
- 현재가보다 위에 있는 매수 슬롯은 시작 또는 복구 직후에는 주문하지 않음

## 매도 흐름

매도 주문은 해당 슬롯의 매수 체결 이후에만 접수한다. 매수 전에는 슬롯 수량이 확정되지 않았기 때문이다.

```text
HOLDING
-> 목표 매도 지정가 주문 접수
-> SELL_PENDING
-> 주문 동기화에서 매도 체결 확인
-> sell fill 저장
-> 실현손익 반영
-> EMPTY
-> 다시 매수 지정가 주문 접수
```

즉 매도도 "현재가가 목표가 이상인지"를 봐서 그때 주문하는 것이 아니라, 매수 체결 직후 목표 매도 지정가 주문을 미리 유지하고 체결 여부를 동기화한다.

## 슬롯 상태값 1차 정리

1차 구현에서는 기존 슬롯 상태값을 유지하되 의미를 선주문형에 맞게 재정의한다.

| 상태 | 선주문/체결동기화형 의미 |
| --- | --- |
| `EMPTY` | 포지션 없음. 열려 있는 매수 주문도 없음. 정상 운용 중에는 매수 주문 보충 대상 |
| `BUY_PENDING` | 매수 지정가 주문이 접수되어 체결 대기 중 |
| `HOLDING` | 매수 체결로 포지션을 보유 중이지만 목표 매도 주문이 없거나 보충이 필요한 상태. 정상 선주문 흐름에서는 짧게 지나가는 중간 상태 |
| `SELL_PENDING` | 목표 매도 지정가 주문이 접수되어 체결 대기 중 |
| `PAUSED` | 현재 enum에 남아 있는 슬롯 격리 상태. 정상 일시정지보다는 주문 실패, 회계 불일치, 수동 개입 필요 같은 비정상 상황에서 자동 운용을 멈추는 의미에 가깝다 |

이 방식은 DB 마이그레이션과 UI 변경 부담을 줄이면서 선주문형으로 전환할 수 있다.

장기적으로는 슬롯 상태와 주문 상태를 더 명확히 분리하는 구조가 바람직하다.

```text
슬롯 상태:
FLAT / HOLDING / FAILED 또는 BLOCKED

주문 상태:
ACCEPTED / PARTIALLY_FILLED / FILLED / CANCELED / REJECTED / FAILED
```

하지만 1차 범위에서는 기존 상태값을 유지한다.

`PAUSED`라는 이름은 전략 또는 러너의 정상 일시정지와 혼동될 수 있다. 슬롯 단위 상태가 비정상 격리만 표현한다면 `FAIL`보다는 상태명 관례에 맞는 `FAILED`, 또는 사용자의 조치가 필요하다는 의미의 `BLOCKED`가 더 명확하다. 단, 1차에서는 DB 마이그레이션을 피하기 위해 이름은 유지하고 설명만 비정상 격리 의미로 좁힌다.

## 러너 역할 변경

기존 러너 역할:

```text
현재가 조회
-> 매수/매도 조건 평가
-> 조건 만족 시 주문 실행
```

변경 후 러너 역할:

```text
현재가 조회
-> 열린 주문 상태 동기화
-> 체결 결과를 슬롯과 fill에 반영
-> 슬롯별로 있어야 할 주문이 없으면 보충
-> 중복 주문 방지
```

러너는 조건 판단자보다 주문 상태 관리자와 복구 담당자에 가까워진다.

## PAPER 모드 정책

PAPER 모드도 선주문형 의미에 맞게 동작해야 한다.

- `paper-limit` 주문은 접수 후 계속 살아 있는 주문으로 취급
- 가격 관측 구간이 지정가를 터치 또는 통과하면 체결
- 지정가를 터치하지 않았으면 `ACCEPTED` 유지
- 동기화 시점의 단일 현재가가 지정가 반대편이라는 이유만으로 자동 취소하지 않음
- 취소는 명시적 취소, 전략 중단, 밴드 재설정, 리스크 정책 같은 별도 전이로 처리

## PAPER_STAGE 설계 방향

PAPER 모드는 실거래 전 검증을 위한 스테이징 모드처럼 사용한다. 핵심은 실제 주문 API를 호출하지 않으면서도 시세, 주문 상태, 잔고 잠금, 체결 동기화 흐름은 빗썸 실거래와 최대한 비슷하게 흉내내는 것이다.

```text
시세/호가/최근 체결 데이터:
실제 빗썸 Public API 사용

주문 생성/취소/조회:
실제 빗썸 주문 API를 호출하지 않고 로컬 mock exchange 사용

응답 구조/상태/검증:
빗썸 API 응답 모양과 제약을 최대한 동일하게 모방
```

PAPER_STAGE에서 호출해도 되는 API:

- `GET /v1/market/all`: 거래 대상 페어 검증
- `GET /v1/ticker`: 현재가 조회
- `GET /v1/orderbook`: 호가와 스프레드 확인
- `GET /v1/trades/ticks`: 최근 실제 체결 데이터 확인
- 선택적으로 `GET /v1/orders/chance`: 주문 가능 정보, 수수료, 최소 주문 금액 확인
- 선택적으로 `GET /v1/accounts`: 실제 잔고 조회와 내부 mock 잔고 비교

PAPER_STAGE에서 호출하면 안 되는 API:

- `POST /v2/orders`
- `POST /v2/orders/batch`
- `DELETE /v2/order`
- 실제 주문 생성, 주문 취소, 출금 관련 모든 API

실제 빗썸 API 키를 사용하는 경우에도 PAPER_STAGE 키는 읽기 전용에 가깝게 제한한다. 가능한 경우 자산조회와 주문조회 권한만 허용하고, 주문하기와 출금하기 권한은 비활성화한다. IP 제한도 함께 사용한다.

### Mock exchange 역할

로컬 mock exchange는 빗썸 주문소의 최소 기능을 흉내낸다.

```text
createOrder
-> 빗썸 /v2/orders 요청과 같은 형태를 검증
-> 로컬 orders 테이블에 ACCEPTED 저장
-> rawResponse에는 빗썸식 order_id, client_order_id, state=wait 저장

listOrders/getOrder
-> 빗썸 /v1/orders, /v1/order 응답과 같은 필드로 로컬 주문 반환

syncFills
-> 실제 ticker/orderbook/trades 데이터를 보고 로컬 주문 체결 여부 판단
-> 체결 시 state=done, executed_volume, executed_funds, paid_fee 반영

cancelOrder
-> 명시적 취소 요청만 state=cancel 처리
```

내부 주문 상태와 빗썸 주문 상태는 다음처럼 매핑한다.

| 내부 상태 | 빗썸 mock 상태 | 의미 |
| --- | --- | --- |
| `ACCEPTED` | `wait` | 주문 접수, 체결 대기 |
| `PARTIALLY_FILLED` | `wait` | 일부 체결, 잔량 대기 |
| `FILLED` | `done` | 주문 처리 완료 |
| `CANCELED` | `cancel` | 주문 취소 |
| `REJECTED` | 없음 또는 400 응답 | 주문 검증 실패 |
| `FAILED` | 없음 또는 5xx/네트워크 오류 | 시스템 오류 |

`rawRequest`에는 실제 빗썸 주문 요청과 같은 필드를 저장한다.

```json
{
  "market": "KRW-USDT",
  "side": "bid",
  "order_type": "limit",
  "price": "1500",
  "volume": "666.400106",
  "client_order_id": "..."
}
```

`rawResponse`에는 실제 빗썸 주문 조회 응답에 맞춘 필드를 저장한다.

```json
{
  "order_id": "paper-...",
  "client_order_id": "...",
  "market": "KRW-USDT",
  "side": "bid",
  "order_type": "limit",
  "price": "1500",
  "volume": "666.400106",
  "remaining_volume": "0",
  "executed_volume": "666.400106",
  "executed_funds": "999600.159",
  "paid_fee": "399.841",
  "state": "done",
  "created_at": "..."
}
```

### 체결 mocking 원칙

PAPER_STAGE 체결은 현재가 한 점만으로 판단하지 않는다. 실제 거래소 주문장과 가까워지도록 아래 순서로 보수적으로 판단한다.

1. 최근 체결 데이터 기반
   - 매수 주문은 실제 체결 가격이 주문가 이하로 발생했을 때 체결 가능
   - 매도 주문은 실제 체결 가격이 주문가 이상으로 발생했을 때 체결 가능

2. 호가 기반 보조 판단
   - 매수 주문가가 현재 매도 1호가 이상이면 즉시 체결 가능성이 높음
   - 매도 주문가가 현재 매수 1호가 이하이면 즉시 체결 가능성이 높음
   - 호가 잔량을 넘는 수량은 부분 체결로 남길 수 있음

3. 틱 구간 기반 보수 판단
   - 이전 관측가와 현재 관측가 사이가 지정가를 통과해도, 실제 체결 또는 호가 근거가 없으면 과도한 낙관 체결을 피함
   - 단, 테스트 편의용 설정으로 구간 터치 체결 모델을 켤 수는 있음

4. 자동 취소 금지
   - 주문가를 터치하지 않았거나 현재가가 반대편으로 이동했더라도 주문은 `ACCEPTED` 상태로 유지
   - 취소는 명시적 취소, 전략 중단, 밴드 재설정, 리스크 정책에서만 발생

### 잔고와 잠금 모델

PAPER_STAGE는 주문 체결뿐 아니라 잔고 잠금도 흉내내야 한다.

```text
매수 주문 접수:
available KRW 감소
locked KRW 증가

매수 체결:
locked KRW 감소
보유 자산 available 증가
수수료 차감

매도 주문 접수:
보유 자산 available 감소
보유 자산 locked 증가

매도 체결:
보유 자산 locked 감소
available KRW 증가
수수료 차감

주문 취소:
잔량에 해당하는 locked 자산을 available로 복귀
```

이 모델을 넣어야 잔고 부족, 중복 주문, 부분 체결, 수동 개입 이후 회계 불일치를 LIVE 전에 발견할 수 있다.

### LIVE 전환 경계

PAPER_STAGE와 LIVE는 같은 주문 요청 빌더와 같은 주문 동기화 파서를 공유하는 것이 좋다.

```text
BithumbOrderRequestBuilder:
PAPER_STAGE와 LIVE가 같은 주문 요청 생성 로직 사용

BithumbOrderMapper:
빗썸 주문 조회 응답을 내부 Order/Fill/Slot 전이로 변환

BithumbPaperExchange:
주문 생성/조회/취소 응답을 로컬에서 mock

BithumbLiveBroker:
같은 요청을 실제 빗썸 API로 전송
```

이렇게 하면 실거래 전환 시 바뀌는 부분은 "로컬 mock exchange에 보내던 요청을 실제 빗썸 주문 API에 보낸다"는 경계에 집중된다.

## 기대 효과

- 틱 지연 때문에 조건 만족 구간을 놓치는 문제 감소
- 실거래 지정가 주문 방식과 PAPER 모드의 의미가 가까워짐
- 매수/매도 판단보다 주문 상태 동기화와 복구가 중심이 되어 장애 후 재개가 명확해짐
- 슬롯별 중복 주문 방지 기준이 단순해짐
- 실제 주문 API를 호출하지 않고도 빗썸 주문/체결/잔고 흐름을 검증할 수 있음
- LIVE 전환 시 주문 요청 생성과 주문 동기화 파서의 변경 범위를 줄일 수 있음

## 구현 시 확인할 점

- 시작/복구 직후 현재가보다 위에 있는 매수 주문을 어떻게 다룰지 정책 확정
- 기존 `BUY_PENDING`, `SELL_PENDING` UI 라벨이 새 의미와 맞는지 확인
- 부분 체결을 슬롯 수량과 평균 체결가에 어떻게 반영할지 결정
- 주문 취소, 거절, 실패 시 재주문 정책 정의
- 슬롯 단위 `PAUSED`를 계속 유지할지, 비정상 격리 의미에 맞춰 `FAILED` 또는 `BLOCKED`로 바꿀지 결정
- 선주문 보충 로직이 같은 슬롯에 중복 주문을 만들지 않도록 보장
- LIVE 모드에서는 거래소 주문 조회 결과를 체결, 미체결, 취소 상태의 기준으로 사용
- PAPER 모드에서는 관측 가격 구간 기반 체결 모델이 필요
- PAPER_STAGE에서 실제 주문/취소 API를 절대 호출하지 않도록 권한, 환경 변수, 코드 경계를 이중으로 막기
- 빗썸 응답 필드인 `remaining_volume`, `executed_volume`, `executed_funds`, `paid_fee`를 내부 주문/체결 모델에 어떻게 보존할지 결정
- 실제 Public API rate limit을 고려해 ticker, orderbook, trades 조회 주기와 캐싱 정책 정의
- read-only 성격의 API 키를 사용할 경우 주문하기/출금하기 권한이 꺼져 있는지 운영 전 확인

## 1차 범위

- 슬롯 상태 enum은 유지
- 상태 의미만 선주문형으로 재정의
- EMPTY 슬롯에는 누락된 매수 지정가 주문을 보충
- HOLDING 슬롯에는 누락된 목표 매도 지정가 주문을 보충
- ACCEPTED 주문은 동기화 대상이며, 단일 현재가 반대편 이동만으로 자동 취소하지 않음
- PAPER_STAGE 1차 구현은 러너가 주입한 시세를 사용하고, 주문 생성/취소는 로컬 mock exchange로 처리
- 실제 빗썸 Public API 시세, 호가, 체결 데이터 직접 연동은 mock exchange 흐름이 안정화된 뒤 별도 단계에서 연결
- mock 주문 응답은 빗썸 `order_id`, `client_order_id`, `state`, `executed_volume`, `executed_funds` 형태를 따른다
- 매수/매도 주문 접수 시 mock 잔고 잠금과 해제를 반영
- 문서, 테스트, UI 라벨을 새 의미에 맞게 정리
