# 빗썸 시세 데이터 파일 캐시 설계

작성일: 2026-06-28

## 배경

현재 자동매매 화면은 전략 시작 시각부터 차트를 보여주기 위해 새로고침 또는 화면 재진입 때마다 빗썸 분봉 API를 다시 호출한다.

이미 한 번 조회한 닫힌 분봉은 값이 바뀔 가능성이 낮기 때문에, 같은 구간을 반복 조회하는 것은 불필요하다. 특히 자동매매 화면이 `activatedAt`부터 현재까지 1분봉을 여러 페이지로 다시 가져오는 구조라서, 전략 실행 시간이 길어질수록 중복 조회가 늘어난다.

목표는 한 번 조회한 빗썸 시세 데이터를 파일로 저장하고, 이후 같은 데이터를 요청할 때는 파일 캐시를 우선 사용해서 빗썸 API 중복 호출을 줄이는 것이다.

## 현재 구조 요약

### 실시간 현재가

- 프론트엔드 자동매매 화면은 `/api/bithumb/ticker`를 주기적으로 호출한다.
- 서버는 빗썸 `/v1/ticker`를 프록시한다.
- 프론트엔드는 응답을 React state에만 보관한다.
- 자동매매 러너는 tick마다 현재가 숫자를 조회해 주문 동기화에 사용하고, SQLite에는 마지막 관측가 1개만 저장한다.

### 자동매매 차트 분봉

- 프론트엔드는 전략의 `activatedAt`을 기준으로 `/api/bithumb/candles/minutes`를 반복 호출한다.
- 서버는 빗썸 `/v1/candles/minutes/{unit}`를 프록시만 하고 파일에 저장하지 않는다.
- 새로고침하면 프론트 메모리는 비워지지만, `activatedAt`이 SQLite에 남아 있으므로 같은 분봉 구간을 다시 빗썸에서 조회한다.

### 백테스트용 과거 캔들

- `data/bithumb/{market}/{interval}/{YYYY-MM-DD}.json` 파일에 저장된 데이터를 `/api/candles`가 읽어 제공한다.
- 현재 저장된 파일 예: `data/bithumb/KRW-USDT/1m/2026-05-10.json`
- 이 파일 구조는 분봉 캐시 저장소로 재사용할 수 있다.

## 캐시 대상

우선순위는 다음과 같이 둔다.

1. 자동매매 차트용 닫힌 1분봉
2. 백테스트와 화면 조회에서 공통으로 쓰는 과거 분봉
3. 필요 시 다른 minute unit 분봉
4. ticker, orderbook, trades는 별도 정책 확정 후 적용

첫 구현 범위는 `GET /api/bithumb/candles/minutes`에서 조회되는 분봉 데이터로 제한한다.

## 캐시하지 않거나 짧게만 캐시할 데이터

### 현재 진행 중인 분봉

현재 시간의 분봉은 아직 닫히지 않았으므로 값이 계속 바뀔 수 있다.

- 파일에 영구 확정값처럼 저장하지 않는다.
- 화면에는 빗썸 최신 응답 또는 ticker로 합성한 값을 보여줄 수 있다.
- 분봉 종료 이후 충분한 지연 시간이 지나면 닫힌 캔들로 간주해 파일에 저장한다.

권장 기준:

- 1분봉은 해당 분이 끝난 뒤 5-10초가 지난 캔들만 확정 저장한다.
- 서버 시각 기준 현재 minute bucket과 직전 minute bucket은 보수적으로 재조회 가능 영역으로 둔다.

### ticker 현재가

ticker는 스냅샷 성격이 강하므로 장기 파일 캐시 대상으로 적합하지 않다.

- 자동매매 판단용 ticker는 매 tick마다 최신값이 필요하므로 파일 캐시를 사용하지 않는다.
- 화면 표시용 ticker는 1-3초 수준의 메모리 TTL 캐시는 가능하지만, 파일 캐시는 기본 범위에서 제외한다.

### orderbook

호가는 아주 빠르게 변한다.

- 실시간 주문 판단이나 유동성 점검에는 파일 캐시를 사용하지 않는다.
- 디버깅 또는 감사 목적 스냅샷 저장은 별도 기능으로 다룬다.

### trades ticks

최근 체결 내역은 cursor, sequential id, 시간 범위 정책이 필요하다.

- 분봉 캐시와 섞지 않는다.
- 추후 슬리피지 분석이나 체결 재현 목적이 생기면 전용 저장 구조를 설계한다.

## 파일 저장 구조

기존 백테스트 파일 구조를 유지한다.

```text
data/
  bithumb/
    {MARKET}/
      {INTERVAL}/
        {YYYY-MM-DD}.json
```

예시:

```text
data/bithumb/KRW-USDT/1m/2026-06-28.json
```

파일 단위는 KST 날짜를 기준으로 한다. 빗썸 분봉 응답에 `candle_date_time_kst`가 있으므로 이를 기준으로 해당 일자 파일에 저장한다.

## 저장 포맷

기본 포맷은 빗썸 원본 응답 필드를 유지한다.

이유:

- 기존 `data/bithumb/...json` 파일과 호환된다.
- `/api/candles`가 이미 원본 캔들을 `normalizeRawCandle`로 정규화한다.
- 추후 빗썸 응답 필드가 필요한 검증이나 감사에 유리하다.

저장 시 정렬 기준:

- `candle_date_time_kst` 오름차순
- 같은 시각 데이터가 중복되면 더 최근에 받은 값을 사용

## 조회 흐름

### 서버 API 책임

`/api/bithumb/candles/minutes`는 단순 프록시가 아니라 파일 캐시 계층을 거치도록 바꾼다.

요청:

```http
GET /api/bithumb/candles/minutes?unit=1&market=KRW-USDT&count=200&to=...
```

처리 순서:

1. 요청 파라미터를 정규화한다.
2. 요청이 포함하는 시간 범위를 계산한다.
3. 파일 캐시에 이미 있는 확정 분봉을 읽는다.
4. 캐시에 없는 구간만 빗썸 API로 조회한다.
5. 빗썸 응답 중 확정된 분봉만 날짜별 파일에 병합 저장한다.
6. 캐시 데이터와 새 응답을 합쳐 기존 빗썸 응답과 같은 배열 형태로 반환한다.

### 프론트엔드 책임

프론트엔드는 가능하면 지금처럼 `/api/bithumb/candles/minutes`만 호출한다.

캐시 여부는 서버 내부 구현으로 숨긴다. 화면 코드는 "빗썸에서 왔는지, 파일에서 왔는지"를 몰라도 된다.

디버깅이 필요하면 응답에 선택적으로 메타데이터를 추가할 수 있다.

```json
{
  "data": [],
  "cache": {
    "hitCount": 180,
    "missCount": 20,
    "source": "file+bithumb"
  }
}
```

단, 기존 화면 호환을 위해 `data` 배열 구조는 유지한다.

## 중복 조회 제거 기준

중복 조회를 없애야 하는 대상은 "이미 파일에 있는 확정 분봉"이다.

다음 조건을 모두 만족하면 빗썸 API를 호출하지 않는다.

- 요청한 market, unit, time bucket이 파일에 존재한다.
- 해당 캔들이 닫힌 분봉이다.
- 파일 데이터가 파싱 가능하고 필수 필드를 가진다.

다음 경우는 재조회할 수 있다.

- 현재 진행 중인 분봉
- 방금 닫힌 분봉처럼 확정 지연 시간 안에 있는 캔들
- 파일이 없거나 깨진 경우
- 요청 범위 중 일부 minute bucket이 누락된 경우
- 명시적인 강제 새로고침 옵션이 있는 경우

## API 호출 최소화 전략

빗썸 minute candle API는 최신 데이터에서 과거 방향으로 조회한다. 현재 프론트엔드 `loadTradingCandles()`도 `to`를 이동시키며 여러 페이지를 호출한다.

캐시 적용 후에는 서버가 다음을 보장해야 한다.

- 파일에 있는 날짜 전체를 다시 빗썸에서 조회하지 않는다.
- 누락된 구간이 여러 개여도 가능한 적은 페이지 호출로 묶는다.
- 최신 미확정 영역만 반복 조회한다.
- 같은 요청이 동시에 들어오면 같은 파일에 병합 쓰기가 충돌하지 않게 한다.

## 파일 병합 규칙

파일 쓰기는 원자적으로 처리한다.

1. 기존 파일을 읽는다.
2. 기존 캔들과 새 캔들을 `market + unit + candle_date_time_kst` 기준으로 병합한다.
3. 정렬한다.
4. 임시 파일에 쓴다.
5. rename으로 교체한다.

부분 쓰기나 프로세스 중단으로 JSON이 깨지는 것을 막기 위해 직접 덮어쓰기는 피한다.

## 캐시 무효화

기본적으로 닫힌 분봉은 영구 캐시한다.

예외 정책:

- 현재 날짜 파일은 최신 미확정 캔들이 섞일 수 있으므로 확정 캔들만 저장한다.
- 파일 파싱 실패 시 해당 파일을 무시하고 빗썸에서 다시 조회한다.
- 수동 재수집이 필요하면 `forceRefresh=true` 같은 옵션을 별도로 둔다.

## 자동매매 판단과의 관계

분봉 파일 캐시는 차트와 과거 데이터 조회 최적화를 위한 것이다.

자동매매 러너의 현재가 판단은 계속 최신 ticker를 사용한다.

이유:

- 지정가 주문 동기화는 현재 시점의 가격이 중요하다.
- 파일 캐시된 분봉은 1분 단위 과거 데이터라 tick 판단용으로 쓰기에는 늦다.
- 시세 캐시 문제로 자동매매가 오래된 가격을 사용하는 위험을 피해야 한다.

## 구현 구조

### 파일 캐시 모듈

구현 모듈:

```text
server/marketDataCache.ts
```

주요 함수:

```ts
readMinuteCandlesFromCache(market, unit, from, to)
mergeMinuteCandlesIntoCache(market, unit, candles)
isClosedMinuteCandle(candle, unit, now)
```

### `/api/bithumb/candles/minutes` 캐시 적용

`/api/bithumb/candles/minutes`는 캐시 read-through 흐름을 사용한다.

원칙:

- 응답 `data`는 기존과 동일하게 유지한다.
- 캐시가 완전하면 빗썸 호출 없이 반환한다.
- 캐시가 일부만 있으면 부족한 부분만 빗썸 호출 후 병합한다.
- `forceRefresh=true`를 주면 파일 캐시 hit 여부와 관계없이 빗썸 API를 다시 조회한다.

### 테스트

구현된 테스트:

- 캐시 파일이 있으면 빗썸 client를 호출하지 않는다.
- 캐시가 일부 누락되면 누락 구간만 요청한다.
- 현재 진행 중인 분봉은 영구 저장하지 않는다.
- 같은 캔들을 두 번 저장해도 파일에는 하나만 남는다.
- 깨진 JSON 파일이 있어도 서버가 죽지 않고 재조회한다.

### 화면 동작 확인

확인 항목:

- 자동매매 화면 새로고침 후 차트가 계속 보인다.
- 같은 닫힌 분봉 구간은 네트워크상 빗썸 호출이 반복되지 않는다.
- 최신 현재 분봉은 계속 갱신된다.
- `/api/candles` 백테스트 조회와 파일 포맷이 충돌하지 않는다.

## 남은 결정 사항

- 캐시 대상은 우선 1분봉만 할지, `unit` 전체로 확장할지 결정해야 한다.
- 현재 날짜 파일에 당일 확정 분봉을 계속 누적할지, 하루가 끝난 뒤만 저장할지 결정해야 한다.
- `forceRefresh` 같은 수동 재조회 옵션을 API에 노출할지 결정해야 한다.
- 응답에 cache metadata를 포함할지, 완전히 내부 구현으로 숨길지 결정해야 한다.
- 기존에 있는 `data/bithumb/KRW-USDT/1m/*.json` 파일을 새 캐시 로직의 신뢰 가능한 초기 캐시로 볼지 검증해야 한다.

## 권장 결론

자동매매 화면 차트에서 반복 조회되는 분봉은 파일 캐시를 적용하는 것이 좋다.

다만 자동매매 판단용 ticker와 호가 데이터는 파일 캐시 대상에서 제외한다. 분봉 캐시는 "과거 차트와 백테스트 데이터 중복 조회 제거"에 집중하고, 실시간 판단은 최신 API 조회를 유지하는 방식이 가장 안전하다.

첫 구현은 기존 `data/bithumb/{market}/{interval}/{date}.json` 구조를 재사용해 1분봉 read-through cache를 만들고, 닫힌 분봉만 영구 저장하는 방향을 권장한다.
